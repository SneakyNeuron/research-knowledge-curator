# Phase 02: LeanRAG baseline spike — Requirements

## Functional
- R1: A developer with Docker, vLLM and an RTX 4090-class GPU can reproduce both baselines from `scripts/spikes/leanrag/README.md` alone:
  - setup, check;
  - synthetic generation, chunking, three builds, queries and measurement;
  - `mix` download, chunking, one build, queries and judge;
  - teardown.
- R2: Upstream LeanRAG runs unmodified from commit `ee2d524cf6e216712122bdbc1fecd0d5b3eec7d3`. No file in the clone is edited. The harness replaces only the `__main__` entry points with its own drivers, which import upstream's functions, and supplies `config.yaml` in its work directory. No upstream code or prompt text is copied into any committed file (upstream has no LICENSE file).
- R3: The synthetic corpus is about 40 articles (each about 2,500–3,500 words) in the `fin-model-evaluation` domain, generated by the baseline chat model from `corpus_spec.yaml`. Each is labelled `synthetic: true` with `generated_by` (model, revision, seed, temperature) per article in `articles.jsonl` and in the fixture README. It contains no third-party text, and authors, venues and references are fictional.
- R4: The synthetic corpus carries controlled content, inserted verbatim by the generator, with a `kind` and recorded character offsets:
  - 2–3 planted facts per article;
  - at least 5 disagreement pairs;
  - 4 canary articles with distinct payload forms (unique `RKC-CANARY-<hex>` tokens, `.invalid` URLs);
  - at least 3 names with SQL, YAML and shell metacharacters.
- R5: `questions.yaml` holds 15–20 questions (kinds `fact`, `disagreement`, `multi-hop`, `seed`, `negative`) with expected planted-fact IDs and `expect_strings`. It includes the 3 `fin-model-evaluation` questions from `docs/topics.md`, at least 2 negative controls, and every disagreement pair. The owner approves it before the first baseline build.
- R6: Chunking is upstream's `chunk_documents` (1024 tokens, overlap 128, `cl100k_base`), with the synthetic output committed unchanged as `chunks.json`. A `chunk_map.jsonl` maps every synthetic chunk to its article and character offsets, with a `split_char` flag for windows that split a multi-byte character, so every retrieved text unit can be traced to source spans.
- R7: Three full synthetic builds (GraphExtraction, `deal_duplicate_entity`, `hierarchical_clustering`) run with identical models, parameters and seed. Each build's extraction outputs, MySQL tables (as JSONL), hierarchy shape and per-stage cost log are committed.
- R8: For every question and build, the harness records the structured retrieval (entities, reasoning paths, aggregation nodes, text units, mapped to spans for the synthetic corpus) and the answer, made with the same calls and settings as `query_graph` (`topk=10`, `level_mode=1`, `k=5`). For the synthetic corpus it also records the context string. One question is checked to produce a context string identical to upstream's `query_graph`.
- R9: Synthetic measurements, per build and across builds:
  - cost per stage (requests, prompt and generation tokens from both vLLM instances, wall time, longest prompt, empty responses);
  - hierarchy shape;
  - traceability (single, multiple or flagged spans);
  - planted-fact recall for LeanRAG and for an FTS5 BM25 baseline over the same chunks, and `expect_strings` hits in answers;
  - disagreement retrieval and survival in summaries;
  - canary survival and spread in generated text, including entity names, matched case-insensitively;
  - metacharacter round-trip after upstream's own normalisation, what upstream strips, and SQL errors and rollbacks;
  - for information: pairwise Jaccard of text-unit and entity sets per question, entity overlap, shape differences, identical extraction or not.

  `tolerance.json` gives each outcome metric's per-build values with min, mean and max, the informational overlaps, and the proposed outcome-based parity rule.
- R10: UltraDomain `mix` baseline:
  - `mix.jsonl` is downloaded from `TommyChien/UltraDomain` at revision `aa8a51d523f8fc3c5a0ab90dd16b7f6b9dbb5d0d` and verified by SHA-256;
  - it is chunked as upstream's `file_chunk.py` does, with the chunk hashes compared with upstream's shipped `mix_chunk.json`;
  - one build and its 130 questions are queried;
  - a pairwise judge (our own prompt; comprehensiveness, diversity, empowerment, overall; both answer orders) compares our answers with upstream's published `mix_lean_answer.jsonl`.

  Committed: the hash comparison, per-question keys, retrieved entity names, text-unit hashes, answers, judge verdicts and win rates, cost log, hierarchy shape and metrics. No `mix` source text, context strings or graph exports.
- R11: The proposed parity rule for phase 8 is outcome-based:
  - synthetic: planted-fact recall, answer hits and disagreement retrieval are each at least the worst of the three builds, and canary spread is at most the worst;
  - `mix`: the judge's overall win rate of phase 8's engine against this build is between 40% and 60%, averaged over both orders.

  The owner approves the rule and its numbers before the phase closes.
- R12: `docs/spikes/leanrag.md` records, in our own words and without upstream code or prompts:
  - setup and the licence finding;
  - input format and chunking, embedding dimension, traceability;
  - cost for both benchmarks, extrapolated to 100 and 1,000 articles;
  - stability and the band, disagreement, injection and metacharacter results;
  - retrieval compared with FTS5, a per-question table, and the `mix` results;
  - limitations, implications for the reimplementation, and the decision.
- R13: The decision recorded is that both baselines exist and phase 8 proceeds, with the approved parity rule as its go/no-go. Phase 2 has no quality gate on LeanRAG itself.
- R14: `specs/roadmap.md` phases 2 and 8 describe this spec (updated in the spec commit). `specs/tech-stack.md`'s project structure names `tests/fixtures/leanrag_baseline/` as the parity baseline.

## Technical
- T1: Models, served by vLLM as two instances sharing one RTX 4090 (24 GB):
  - Baseline chat: `stelterlab/Qwen3-30B-A3B-Instruct-2507-AWQ` (4-bit), `--max-model-len 32768`, `--kv-cache-dtype fp8`. Fallback: 16,384 if the dev run shows 32k does not fit, recorded, with over-length requests treated as findings.
  - Dev chat: Qwen3-4B-Instruct-2507, used only for harness development.
  - Embedding: Qwen3-Embedding-0.6B, 1024 dimensions, `--runner pooling`.

  The fixture README records the exact Hugging Face repos and revisions, quantisation, vLLM version and the full `serve` command lines.
- T2: All chat calls use `temperature=0` and one fixed `seed`, passed as request kwargs through upstream's `InstanceManager`, which also sends `enable_thinking: False`. Upstream's clustering randomness is left as it is: UMAP runs without a `random_state` (so the hierarchy can differ between builds even at temperature 0) and the Gaussian mixture uses `random_state=0`. The judge uses the same chat model, temperature and seed. The one exception is regenerating a corpus article that failed: at temperature 0 another seed changes nothing, so a retry uses a temperature above 0 and a new seed, both recorded for that article.
- T3: Endpoints and model names come only from environment variables. No key or secret is written to any file. The harness writes `config.yaml` with `yaml.safe_dump` into its gitignored work directory, with exactly the keys upstream reads (`deepseek.model`, `deepseek.api_key` as a fixed non-secret placeholder, `deepseek.base_url`, `glm.model`, `glm.base_url`).
- T4: The harness venv is Python 3.12, created by `uv`, with upstream's `requirements.txt` installed exactly (pins unchanged) plus `pytest`. Nothing is added to `rkc`'s `pyproject.toml` dependencies or `uv.lock`.
- T5: MySQL runs from `mysql:8.4.13` in Docker, published only on `127.0.0.1:4321`, with upstream's hard-coded `root`/`123`. That credential is accepted because the container is localhost-only and throwaway. `root` authenticates with `mysql_native_password` (`--mysql-native-password=ON`), so upstream's pinned PyMySQL can log in without `cryptography`. Its data volume is removed by teardown.
- T6: Gitignored: the upstream clone, the harness venv and the work directory (generated config, tiktoken cache, downloaded `mix.jsonl`, Milvus Lite files, raw logs). No Milvus file, PDF, third-party text or upstream code is committed.
- T7: Harness code passes `uv run ruff check .` and `uv run ruff format --check .` under the repo's configuration. The only `pyproject.toml` change is an `S101` per-file ignore for the harness's tests. Harness tests:
  - use their own `scripts/spikes/leanrag/pytest.ini`, and are not collected by the main `pytest` run or type-checked by `mypy`;
  - need no network, because tiktoken's encoding is prefetched into `TIKTOKEN_CACHE_DIR` by setup;
  - run with `cd scripts/spikes/leanrag && TIKTOKEN_CACHE_DIR=<work>/tiktoken <venv>/bin/pytest -q`.
- T8: The main suite gains `tests/test_leanrag_baseline_fixture.py`: standard library only, offline, checking the committed synthetic fixtures' internal consistency (R3, R4, R6, T10, T11). `scripts/check.sh` passes.
- T9: Cost is measured from both vLLM instances' Prometheus `/metrics` counters (`vllm:request_success_total`, `vllm:prompt_tokens_total`, `vllm:generation_tokens_total`), read before and after each stage, plus wall-clock time. An embedding (pooling) instance generates no tokens, so `check` and the measurements require only the request and prompt-token counters there and report a missing `vllm:generation_tokens_total` without failing. The adapter counts empty responses and records the longest prompt, measured in `cl100k_base` tokens (the tokenizer upstream truncates with) on the messages as sent after upstream's in-place truncation; exact served-model token totals come from the `/metrics` deltas, because upstream's `InstanceManager` returns `""` on any request error. Requests vLLM rejects never reach `request_success`.
- T10: Synthetic text is NFKC- and whitespace-normalised before offsets are computed and before it is committed. Each planted string occurs exactly once in its article.
- T11: Committed fixtures live in `tests/fixtures/leanrag_baseline/`, hold only `.txt`, `.json`, `.jsonl`, `.yaml` and `.md` files, and stay under 25 MB in total.
- T12: Model-written text in the fixtures (article prose, entity and relation descriptions, summaries, answers, judge verdicts) is labelled as generated in the fixture README, in line with the constitution's rule that generated text is always marked.
- T13: The build driver fails a build when `<working_dir>/milvus_demo.db` is missing after clustering, and uses build names that are valid unquoted MySQL identifiers.
- T14: The FTS5 baseline builds its query from double-quoted word tokens joined by `OR`, passed as a bound parameter.

## Out of scope
- Real papers, arXiv or OpenAlex fetching, and PDF extraction (phases 5 and 7). A real-paper run is phase 13's end-to-end check.
- CommonKG extraction, and UltraDomain domains other than `mix`.
- Any change to upstream code, including fixes for findings. Fixes belong to phase 8's reimplementation.
- A go/no-go gate on LeanRAG's quality. Parity and its consequences are phase 8's.
- Updating the constitution from vendoring to reimplementation (`/sdd:replan` right after this spec is committed).
- Running the harness in CI, on macOS or Windows, or with hosted models.
- The `rkc` input guard. Canary results here describe upstream's behaviour without any guard.
- Choosing the engine's embedded vector index (phase 8).

## Decisions
| Decision | Choice | Reason | Decided in |
|---|---|---|---|
| Phase scope | Keep as one phase | Baseline and findings belong together; phase 8 needs both | spec interview |
| Extraction path | GraphExtraction | No seed entity list; suits a specialist domain; the path the paper's results use | spec interview |
| Corpus | ~40 synthetic articles × ~3k words, committed | Most real papers' licenses do not allow redistribution, while a parity test needs its input in the repo; synthetic content also gives known answers. Replaces the roadmap's 50–100 real papers | spec interview; wording corrected in due diligence |
| Corpus generation | Script with local Qwen3-30B-A3B writing prose, planted items inserted verbatim | Exact offsets for ground truth; generated once and frozen | spec interview |
| PDF step | None; plain text | The spike measures the engine; PDF extraction is phase 5's | spec interview (supersedes the earlier "same extraction stack as rkc" answer, which assumed real PDFs) |
| Chat models | `stelterlab/Qwen3-30B-A3B-Instruct-2507-AWQ` for the baseline, Qwen3-4B-Instruct-2507 for development | 4B is too weak to separate engine quality from extractor quality; 30B-A3B fits a 4090 at 4 bits and runs fast (about 3B active parameters); the 2507 Instruct models do not think, so no `<think>` output breaks upstream's parser; Qwen publishes no official 4-bit build, and this is the smallest community AWQ build (16.7 GB) | spec interview; repo chosen in due diligence |
| Context length | 32,768 with fp8 KV cache; 16,384 fallback | Upstream truncates prompts only at 31,000 tokens; at 16k, community-report prompts fail silently every time | spec review |
| Embedding model | Qwen3-Embedding-0.6B (1024 dimensions), `--runner pooling` | Owner's choice; matches upstream's hard-coded 1024; vLLM auto-converts it as a pooling model | spec interview; flag from due diligence |
| Serving | vLLM, two instances on one RTX 4090 | Owner's hardware and choice | spec interview |
| Determinism and build count | Three synthetic builds, temperature 0, fixed seed | Three pairwise comparisons give a usable band; low variance makes parity meaningful | spec interview |
| Go criterion | Phase 2 records the baselines; phase 8's parity is the go/no-go; findings are not gates | Owner: success means the engine reproduces upstream's results | spec interview |
| Upstream licence | No LICENSE file; phase 8 reimplements from the paper, credits paper and repo in the README; no upstream code or prompts in committed files | Without a licence the code cannot be vendored; algorithms are not protected, code and prompt text are | due diligence, then owner |
| Parity rule | Outcome-based (recall, answer hits, disagreement ≥ worst build; canary spread ≤ worst; `mix` win rate 40–60%); overlaps informational; owner approves numbers at phase end | A reimplementation's own prompts change chunk and entity sets even when it works as well | owner, after due diligence |
| Second benchmark | UltraDomain `mix`, one upstream build, downloaded at a pinned revision, not committed | Upstream's own benchmark shows the engine reproduces the paper's setting; one build because it is about 8× the synthetic cost; variance comes from the synthetic builds | owner, after due diligence |
| `mix` judge | Our own pairwise prompt over the paper's four criteria, both orders, local chat model | Upstream's judge prompt cannot be copied (no licence); pairwise in both orders is robust to position bias | spec drafting, after owner decision |
| MySQL | `mysql:8.4.13` in Docker, `127.0.0.1:4321`, upstream's fixed credentials, native-password root | Upstream hard-codes the credentials; pinned PyMySQL needs `cryptography` for MySQL's default authentication, and 9.x has dropped native passwords | spec interview; image and authentication from due diligence |
| Fixture location | `tests/fixtures/leanrag_baseline/` | Phase 8's parity and engine tests read them; they outlive the harness | spec interview |
| Committed outputs | Synthetic: corpus, chunks, offset map, questions, per-build exports, query results, metrics, band. `mix`: hashes, entity names, answers, judge results, metrics. No Milvus file, no `mix` text | Phase 8 needs a machine-readable target; the vector file is derived; `mix` texts are third-party | spec interview; `mix` part after due diligence |
| Harness quality bar | ruff clean; offline tests in the harness venv for the adapter, generator, offset mapper, build helpers, metrics and judge; own `pytest.ini`; no mypy | Only these parts can silently corrupt the baseline; the code is deleted in phase 8 | spec interview; adapter test and `pytest.ini` from spec review |
| Questions | 15–20 synthetic with known answers, owner approves; `mix`'s 130 as shipped | Enough for a band and parity; known answers make recall objective | spec interview |
| Model access in the harness | Upstream's own `InstanceManager` pointed at vLLM, with temperature and seed as kwargs | Keeps upstream's truncation and request shape; no patching | spec drafting |
| Upstream commit | `ee2d524cf6e216712122bdbc1fecd0d5b3eec7d3` (2026-07-07) | Latest at spec time, still `HEAD` in due diligence | spec drafting |
| Harness Python | 3.12 | Upstream's pins resolve only on 3.11–3.13; 3.12 is rkc's minimum | spec drafting; verified in due diligence |
| Keyword comparison | SQLite FTS5 BM25 over the same chunks, quoted OR query as a bound parameter | Same mechanism as rkc's planned keyword fallback; standard library only; safe against FTS5 syntax in questions | spec drafting; query form from spec review |
| Split characters | `split_char` flag in `chunk_map`; comparisons drop the partial edge character and the U+FFFD run, and skip stripping the span on that side | tiktoken windows can split a multi-byte character, so an exact comparison would always fail there; upstream's `strip()` stops at U+FFFD | spec review; edge rule from Group 3 implementation |
| Flagged-window test characters | `ŝ` and `ꞵ` | `é`, `—` and `β` are whole tokens in `cl100k_base` and can never be split (checked against the vocabulary and by brute force), so they cannot produce a flagged window | Group 3 implementation |
| `chunk_map.jsonl` join keys | Records also carry `chunk_index` and `hash_code` | Joining to `chunks.json` by line order alone is fragile | Group 3 implementation |
| Metacharacter round-trip | Compared after upstream's own normalisation; what it strips reported separately | Upstream upper-cases, unescapes HTML and removes `"` on purpose | spec review |
| Embedding-instance metrics | `check` and measurements require `request_success` and `prompt_tokens` on the embedding instance; a missing `generation_tokens` there is reported, not failed | A pooling model generates nothing; vLLM's docs do not say whether it exports the counter, and failing on it would block every run | owner, Group 1 implementation |
| Longest-prompt tokenizer | `cl100k_base`, measured after the call on the messages as sent | It is the tokenizer upstream truncates with, so it shows how close prompts come to upstream's caps; exact Qwen token totals come from vLLM's `prompt_tokens` deltas | owner, Group 1 implementation |
| README run order | Each group adds its own command to the harness README's run order as it builds it | Fixing command names before the scripts exist would bind later groups | owner, Group 1 implementation |
| Canaries in generator prompts | Never shown to the model; inserted verbatim after the prose is written | A model that saw them could repeat or obey them, breaking the exactly-once check | owner, Group 2 implementation |
| References sections | Built from each article's `references` (other synthetic articles) with no model call; planted items for References are appended after the entries | Keeps references fictional (R3) and gives the reference-entry canary a real list | owner, Group 2 implementation |
| Planted-fact count | "2–3 per article" counts `kind: fact` only; disagreement, canary and metachar items come on top | Same reading as the Group 4 count-by-kind test | owner, Group 2 implementation |
| Model revision | Required `--model-revision` flag on `generate` | vLLM's API does not report the served revision | owner, Group 2 implementation |
| `generated_by` scope | Per article in `articles.jsonl` | A regenerated article records its own seed and temperature | owner, Group 2 implementation |
| Normalisation | NFKC; each line stripped at both ends; paragraphs separated by one blank line; one trailing newline | Stricter than trailing spaces only, harmless for prose, keeps the exactly-once check simple | owner, Group 2 implementation |
| Article length | 2,500–3,500 words reported as a warning, not a failure | Model output length is unreliable; the owner judges it in the Group 4 review | owner, Group 2 implementation |
| Retrying a failed article | `generate --only synthetic:NN --retry-temperature T` with a new `LEANRAG_SEED`; normal generation stays at temperature 0 | At temperature 0 a new seed reproduces the same failing prose | owner, after Group 2 hardening |
| Fixture integrity in the main suite | Stdlib-only offline test, including R4 counts by `kind` | Protects the parity target in CI for as long as it exists | spec drafting; counts from spec review |
