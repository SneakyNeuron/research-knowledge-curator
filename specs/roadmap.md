# Roadmap

Each phase is one feature: planned with `/sdd:feature`, built with `/sdd:implement` and closed with `/sdd:validate`. Phases name the sections of the archived design (`specs/backlog/2026-10-28-design-v3.1.md`) worth reading when their feature spec is written. That design predates the 2026-11-02 pivot from claim curation to original-text indexing, so the constitution wins wherever the two differ.

The MVP (phases 1–13) is a secured system that pulls papers, checks them for attacks and relevance, indexes the original text in LeanRAG, and lets agents query it. LeanRAG is the backbone and is reimplemented from its paper in `rkc` (upstream has no license; decided in the 2026-11-03 replan), so its baseline spike comes first: it records the reference behaviour our engine must match on outcomes, and what upstream accepts and returns shapes the store. The classifier evaluation (phase 5's manual task) needs the owner and network access too, and can start alongside phases 2–4.

- [x] GitHub Actions workflow on Python 3.12 and 3.14

## Phase 2: LeanRAG baseline spike (manual, owner)
Spec: specs/features/02-leanrag-baseline-spike/
Goal: committed baselines of upstream LeanRAG that phase 8's engine must reproduce (a synthetic corpus with three builds and their tolerance band, and upstream's own UltraDomain `mix` benchmark with one build), plus the findings that shape the engine.
- [ ] A throwaway harness in `scripts/spikes/leanrag/`: upstream cloned at a pinned commit into a gitignored directory and run unmodified from its own Python venv created by `uv`, models served locally by vLLM, and a temporary MySQL container bound to localhost for the harness only (`rkc` itself never needs services). Upstream has no LICENSE file, so no upstream code or prompt text is copied into committed files
- [ ] A synthetic corpus of about 40 `fin-model-evaluation` articles, generated by a local model with planted facts, disagreements, injection canaries and metacharacter names inserted verbatim, plus 15–20 owner-approved questions with known answers, committed in `tests/fixtures/leanrag_baseline/` (real papers cannot be committed; real text is exercised in phase 13)
- [ ] Three synthetic builds with upstream's chunking and GraphExtraction, structured query results per question, and the measurements (cost, traceability to source offsets, stability, disagreement, canary survival, metacharacter handling, recall against an FTS5 baseline), committed with `tolerance.json`
- [ ] UltraDomain `mix` (downloaded at a pinned revision, not committed): one upstream build, its 130 questions, and a pairwise judge against upstream's published answers
- [ ] Record the findings, implications for the reimplementation, the owner-approved outcome-based parity rule and the decision in `docs/spikes/leanrag.md`. The phase does not gate on LeanRAG's quality: phase 8's parity check is the go/no-go
Design reference: "Step 9", "LeanRAG engine" (Docker for `rkc`, unmodified use, `engine install` and the sandboxed build do not apply).

## Phase 3: Configuration and cluster init
Goal: clusters and research agents can be created, validated, approved and paused.
- [ ] Pydantic models for `cluster.yaml` (including engine settings: extraction, summary and embedding models, index parameters) and agent YAML (context, sources, triage model, caps), with errors that name the file and field
- [ ] Secrets from the environment or `.env`, redaction, and the approval hash over context, sources and specs
- [ ] `rkc init`, `rkc agent add | validate | approve | list`, `rkc pause | resume`
- [ ] ID validation. `approve` needs an interactive terminal
Design reference: "Step 2", "Cluster layout and configuration".

## Phase 4: Intake store and cache
Goal: an append-only record of what entered the knowledge base and why, with the original text kept unchanged.
- [ ] Schema with migrations: sources, intake decisions (with relevance reason), runs and changesets, watermarks, ban list
- [ ] As-of reads, `retract` of a run, and FTS5 over the normalized source text
- [ ] Hash-addressed cache for payloads and extracted text, NFKC and whitespace normalization, offset locators, cache-only deletion
- [ ] `rkc log`, `rkc show <source>`, `rkc verify` (cache integrity by hash)
Design reference: "Step 3", "Step 4", "Knowledge store" (claim tables do not apply).

## Phase 5: Scanner, ban list and sandboxed extraction (input guard)
Goal: poisoned content is detected, banned and deleted before it is stored, indexed or read by a model.
- [ ] Sandboxed text extraction (PDF and local files) with resource limits, an allowlist of readers, and hidden PDF text as a separate view
- [ ] Normalization, recursive decoding, linear-time rules, the classifier interface with a loud rules-only mode, and fail-closed policy
- [ ] Ban actions, the verdict cache, `rkc scan`, `rkc ban list | show | release`, and the output sanitizer exported for later use
- [ ] Security corpus (including poisoned PDFs) and `scripts/scanner_eval.py` (offline with a stub classifier)
- [ ] Manual (owner): run the classifier evaluation and record the default in `docs/spikes/scanner.md`
Design reference: "Step 5", "Injection defense".

## Phase 6: Model layer, relevance triage and `doctor`
Goal: any configured model can be called safely, papers get a relevance decision, and the environment can be diagnosed.
- [ ] Role-based chat and embedding models (triage, and the engine's extraction, summary and embedding roles), structured calls with one retry, usage counting, scripted fakes and deterministic fake embeddings
- [ ] Provenance prompt template with an untrusted block, and the triage call (relevant or not, capped reason)
- [ ] `rkc doctor` (Python, FTS5, cluster, scanner, classifier, model connectivity per role, keys by name only; the engine store and vector index checks are added in phase 8)
Design reference: "Step 6", "Models", and triage in "Curation workflow".

## Phase 7: Sources
Goal: papers from arXiv, OpenAlex and local files arrive as guarded, deduplicated full text.
- [ ] `Article`, the adapter protocol, and the arXiv adapter (metadata, watermarks, PDF download within the rate limit)
- [ ] OpenAlex adapter (abstract reconstruction, retraction flag, full text from OpenAlex's content endpoint within its allowance, abstract fallback)
- [ ] Namespaced identity, ban checks, the input guard before any write, and triage before indexing
- [ ] `rkc add-file --as literature|experiment|note`
Design reference: "Step 7", "Sources".

## Phase 8: LeanRAG engine (reimplemented) and queries
Goal: `rkc query` returns sanitized, untrusted-marked results through our LeanRAG reimplementation, each labelled as verbatim source text or engine-generated, falling back to keyword search.
Process: one phase, implemented end to end without per-group owner supervision; the parity test against the phase 2 baselines is the deciding check, and the owner reviews once at the end (decided in the 2026-11-03 replan).
- [ ] Implement the paper's algorithm in the `engine_leanrag` subpackage with our own code and freshly written prompts, to our gates (`ruff`, `mypy --strict`), with `PROVENANCE.md` (paper citation, upstream repository link and the commit phase 2 compared against, a map from each part of the paper to our module, and every deliberate departure with its measured reason). A clean-room check (`git grep -F` over sample lines of upstream's code and prompts) finds nothing outside `specs/`. Pin its numeric dependencies, model calls through `llm` (extraction, summary and embedding roles), SQLite `graph.sqlite`, and the embedded vector index chosen and recorded here (Milvus Lite 3.x, `sqlite-vec` or brute force)
- [ ] Enforcement in code for the in-process engine: no tools, provenance-marked untrusted block, structured and capped output, parameterized SQL, keys only from hashes and namespaced IDs
- [ ] Engine protocol, `Hit` with the verbatim or generated label and source locators, hydration from the store with the output guard, and a reusable contract test with a scripted fake model and deterministic fake embeddings
- [ ] Full build from the store and cache, `rkc query`, and parity with the phase 2 baselines (`tests/fixtures/leanrag_baseline/`, synthetic and UltraDomain `mix`) under the parity rule approved in phase 2. Parity is the go/no-go: if the engine cannot reach it, agree a different engine with the owner before continuing. Remove `scripts/spikes/leanrag/` once the engine reaches parity
- [ ] CI runs the engine tests on Linux, macOS and Windows
Design reference: "Step 10", "Engines", "Retrieval", "LeanRAG engine" (Docker, MySQL and Milvus services, unmodified use, `engine install` and the sandboxed build do not apply).

## Phase 9: Partial engine updates
Goal: intake keeps the engine current without rebuilding the whole hierarchy, and a full rebuild happens only on request.
- [ ] Partial update on sync: new sources are chunked, extracted and attached to the nearest existing clusters, retracted sources are removed, and only the ancestors of changed nodes are re-summarized
- [ ] `rkc engine sync | rebuild | status`, with `status` reporting drift signals (such as updates since the last rebuild)
- [ ] Measure drift: retrieval after a series of partial updates compared with a fresh full rebuild on the same sources, recorded in `docs/spikes/leanrag.md`, and partial updates recorded as a departure from the paper in `engine_leanrag/PROVENANCE.md`

## Phase 10: Run orchestration
Goal: `rkc run` executes an agent end to end, idempotently, with clear exit codes.
- [ ] Lock, approval check, watermarks, dedupe, input guard, triage, caps, `--dry-run`, engine sync, and the run summary
- [ ] Exit codes for caps, locks, approval drift and scanner failure. Respect pause
Design reference: "Step 11", "Caps and dry-run".

## Phase 11: Scheduling
Goal: agents run on cron without touching anything else in the crontab.
- [ ] `rkc schedule install | remove | show`, with a fixed command template and validated IDs
Design reference: "Step 12", "Scheduling".

## Phase 12: Security smoke suite and report
Goal: evidence that the defense contains injection, including payloads the guards miss.
- [ ] Cases, network blocker, instrumented stubs, a deliberately vulnerable stub of the triage and query paths, a regression corpus, a best-of-N budget and a `live` mode
- [ ] Cases for model-generated text presented as source text, for URLs in fetched content trying to steer downloads, for injection through the engine's extraction and summary prompts, and for entity or relation names (model output) trying to build SQL, paths or configuration in `graph.sqlite`
- [ ] `scripts/security_smoke.py` writes the report (results per objective, failures with evidence, benign controls, what is not covered)
Design reference: "Step 13", "Test scenarios", "Injection defense".

## Phase 13: Skills, docs, end-to-end check and release
Goal: a developer installs `rkc` from PyPI and a coding agent sets it up through skills.
- [ ] `rkc-setup`, `rkc-query`, `rkc-ops`, `rkc-report`, and `rkc skills install --target`
- [ ] `docs/limits.md` and a finished README (supported platforms, and the LeanRAG credit added in the 2026-11-03 replan, now also linking `engine_leanrag/PROVENANCE.md`)
- [ ] Automated end-to-end test, a `uv build` wheel that installs with `uv tool install` and runs the engine on Linux, macOS and Windows, and the first PyPI release
Design reference: "Step 14", "Verification".
